A: one loop, one hub, one clock

spec PR merge→ main evidence→ coordinator: reconcile + cut + admit + close→ coder→ reviewer→ auto-merge↺
  • The hub does four jobs in one run. It compares spec with evidence, cuts the whole gap list into issues, admits, and closes. One sandboxed agent, one serialized run.
  • One clock. The hub wakes only when main gets a new evidence report. A failed coder run, a closed PR, a human who wants to reorder: nothing moves until the next merge or a manual workflow_dispatch.
  • The ask disappears. After the spec merges, the hub regroups requirements across all asks. The person who wrote #12 cannot see what became of it, and the plan is invisible until the scope is frozen.

To-be: version C

C keeps every V2 rule about the spec, the evidence and the merge. It changes how the work is cut, queued, built and closed: five small workflows, each with its own clock, instead of one coordinator that one event wakes.

C: five workflows, each with its own clock

analyze · per ask→ schedule · per repo→ implement · per issue→ review · per PR→ settle · per merge↺
  • Plan with the ask, before the queue. The plan for #12 is made right after its spec merges, from its own requirements, and it is a comment a person can read and /replan.
  • The stand-up is code. No model decides what starts. The scheduler is a short script that runs on every signal: a new queued issue, a run that ended, a merge, a closed PR, /implement, and every 10 minutes.
  • Programs gate, models propose, people decide. The same V2 split of authority, applied to the build: the PR checks on a draft PR with no secret, an attempt cap, a short deny list for the coder, and three named exits when the work cannot go on.

Nothing in C needs a new service, a database or a workflow engine. It is still GitHub Issues, Actions, branch protection and Fullsend.

What A needs and C does not

The holes table lists what A lacks. This section lists the opposite: two things A must have only because one coordinator wakes on one run. C drops both. Each part shows where the job went, so nothing is lost.

Where main evidence went

A runs the full suite on main after every merge and writes the evidence report. That run has no box in C's map. V2 needs it for three reasons, and C keeps all three. It only moves the measurement in front of the merge, where the merge queue already builds the commit that main will become.

What the run on main solvesIn AIn C
A merged SHA nobody tested. A PR's checks run on its head against the main of that moment. Squash merge makes a new SHA. Two PRs that pass alone can fail together.The run on main finds the break after it landed. main is red until a fix merges.The merge queue builds main plus the PR as one commit and runs the suite on it. main fast-forwards to that commit only when it is green. The break is found in the queue. main is never red.
Closure needs proof on main, not on a branch: "a managed issue closes only from latest-main evidence".The coordinator reads the report of the run on main.The scheduler reads the report of the queue check, keyed by the SHA that main now points to. Same rule, same SHA, same report format. One run instead of two.
The whole spec stays measured: which active requirements have no passing test.The coordinator reads the same report and regroups the world.The gap watch reads the same report after every merge. A spec-only merge runs no test: the report script copies the last results and adds the new IDs with 0 tests.
A clock. In A the run is the only event that wakes the coordinator.workflow_run: completed of the run on main.No clock here. The scheduler wakes on "PR merged", and on every other signal (H6).

What it costs: a ruleset on main that requires the merge queue, squash, and the check on the merge_group event; a public repository or a Team plan; no direct push to main; and one more case, a text conflict in the queue, which the scheduler answers with one rebase run (step 16). What is gone: the main evidence workflow, a second full-suite run per merge, the window in which main is red, and the workflow_run wake-up. V2 does not mention the merge queue.

Where the status issue went

A needs one issue that a person creates by hand and that never closes: the coordinator status issue. C has no such issue. This is hole H12, and here is the why in one place.

The Fullsend runs

Seven runs go through Fullsend's runner: triage, the conflict check, the plan run, the test author, the coder, the reviewer and the fix agent. Two things are the same for all of them. Each belongs to one issue or PR, and each is one CI job in three parts, where only the middle part is a model. First what each run belongs to, then the three parts.

What each run belongs to

Fullsend's runner starts a run for one issue or one PR. It needs the number and the URL in the event payload, and it posts its status and run links there (V2 §8.4 and Appendix C). A plain Actions job has no such rule. A's coordinator run belongs to nothing, so A needs a human-made status issue that never closes (H12). In C every run belongs to a real thing. One rule makes this hold: a spec PR that adds a requirement must carry a Source #N line, and every new requirement a sources entry. The spec PR checks fail without them (step 5). So a new requirement with no issue cannot merge green, and every merge that adds one has a plan run with a subject. A spec PR with two sources starts two plan runs. A spec PR that adds no requirement, such as a wording fix in Vision.md or a retirement, needs no issue and starts no plan run. V2 does not have this rule; it calls the source issue a hint.

How each run goes: pre-script, agent, post-script

A Fullsend run is one CI job in three parts, and only the middle part is a model. The pre-script runs on the host before the sandbox exists: it checks the trigger and stages the inputs. The agent runs in a sandbox with a read-only token: it writes files and one result file, and it can never push, label or comment. After the sandbox is torn down, a validation loop checks the result file against a schema, at most twice. Then the post-script runs on the host with the write token: it checks the result again and does every write to GitHub. The map draws all seven runs this way. Labels on the two kinds of issue source issue and managed issue · open

Labels are a view for people. The scheduler rebuilds its picture from them on every run, so a label a person changes by hand changes the queue. One label rides on both kinds of issue: priority:p1 to priority:p4. Triage sets p3 on a source issue that has none. The plan run copies the label of the source issue to each managed issue it writes, or p3 if there is none. The scheduler starts p1 first. A person can change the label on either issue at any time. The top strip is the normal path, the lower strip the exits.
