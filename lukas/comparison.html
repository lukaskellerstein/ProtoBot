Architecture review · autonomous SDLC systems

Four takes on the same problem

ProtoBot, DEX, Forge and Fullsend all try to turn human intent into merged code with agents doing the work in between. They disagree about almost nothing structural and almost everything else. This is what they share, where they split, and which of them is right at each fork.

01

What all four already agree on

These were reached independently, by four teams, from different starting points. That makes them close to settled answers rather than opinions — and it means any new design that contradicts them needs a strong reason.

  1. The orchestrator is code, never an LLM.

    Fullsend states it outright in ADR 0018 after a coordinator agent silently skipped declared subagents and improvised — stronger prompting reduced but never eliminated it. Forge calls the same thing "workflow first, agents second". DEX makes feature selection a deterministic read of feature-manifest.json with no model call at all, and constrains its one LLM decision point to five enum values. ProtoBot gives the Job Site ownership of dispatch. Everyone converged on: agents do bounded domain work, code decides what runs.

  2. Bounded context per unit of work.

    Fresh agent per stage (DEX), one agent per step (Fullsend), ephemeral container per task (Forge), Worker per work item (ProtoBot). Nobody defends the long-lived session. DEX cites the Ralph Wiggum loop, ProtoBot cites Yegge's agent-dementia writeup — same conclusion.

  3. Structured handoffs, not prose.

    DEX uses JSON-schema-constrained output at the boundaries that matter. Fullsend enforces output schema at the harness level with a two-retry validation loop. ProtoBot wants ears-manager precisely so agents stop re-interpreting prose after every compaction. All three cite the same underlying failure: markdown plans get re-decomposed, schemas don't.

  4. Agents never write directly to external systems.

    Forge: implementation agents write only inside their container; the integration layer performs Jira and GitHub mutations at explicit workflow steps. Fullsend: pre-script fetches, sandbox reasons, post-script mutates — and the sandbox holds no credentials to mutate with. ProtoBot adopted this pattern explicitly from Fullsend. It is the strongest security consensus in the set.

  5. Review is a parallel fan-out, not one pass.

    Fullsend's review orchestrator dispatches concurrent sub-agents per dimension — correctness, security, intent, style, docs currency — then deduplicates and synthesises. ProtoBot's Inspector roster is the same shape. Forge runs local review, then implement-review, then AI review as distinct nodes. DEX is the outlier here, and it costs it (see 03).

  6. Git is the audit substrate.

    ProtoBot commits to merge commits all the way down so the full iteration history stays a navigable DAG. DEX writes a machine-parseable [checkpoint:step:cycle] trailer on every stage commit. Forge and Fullsend reflect everything back into the tracker and the PR. Nobody built a bespoke event store.

02

Where they genuinely split

Axis 1 — What is the durable source of truth for intent?

This is the deepest divergence in the set, and the two extremes are ProtoBot and Fullsend.

ProtoBot makes the specification the product: EARS requirements in a machine-validated, queryable store, with code as a regenerable artifact. Fullsend takes the opposite position — intent is the issue title and body, deliberately excluding the comment thread to stay bounded and injection-resistant. Forge sits between: intent is a chain of generated artifacts, each individually human-approved. DEX uses spec-kit specs — structured, but prose, with no well-formedness gate.

Fullsend has an entire unsolved-problem document named intent-representation.md. They know this is their weak flank. ProtoBot is the only one of the four attacking it directly, and that is its single most valuable contribution.

Axis 2 — Where does the human stand?

ProtoBot places one gate early and then goes fully autonomous through merge. Forge places five gates plus a mandatory human PR review. That is a wide spread — and it is inverted relative to the stakes. Forge produces production code and gates heavily; ProtoBot produces disposable demo prototypes and gates once.

DEX is doing something categorically different that is easy to miss: it has no approval gate after clarification, but the timeline gives post-hoc control — jump to any stage, fork a branch mid-run, delete a version, promote a different one to main. That is an undo tree, not a gate. For prototyping, where the answer to "is this right?" is usually "let me see the other version", an undo tree is worth more than an approval queue.

Axis 3 — Trust model

Fullsend is far ahead, and its reasoning is first-principles rather than checklist-driven: prompt injection cannot be reliably prevented, therefore any credential inside a sandbox must be assumed exfiltrable, therefore the default posture is zero credentials in the sandbox. ADR 0016's unidirectional control flow — no layer may reconfigure any layer above it — is a genuine structural invariant that the other three lack entirely.

Forge is solid but simpler: no Jira/GitHub/Redis credentials in containers, rootless Podman, HMAC webhooks — but blanket network isolation with no L7 policy. ProtoBot has the right instincts and no design. DEX has no trust boundary at all, which is coherent for a desktop app and a hard wall if it ever needs to run unattended.

Axis 4 — Where does the machinery live?

Fullsend's decision to run as a CI job with no server is the biggest adoption advantage in the set. There is nothing to deploy, nothing to operate, nothing to get budget for. Forge needs FastAPI, Redis and a Podman host — real infrastructure with a documented single point of failure. DEX needs nothing but a laptop and can never be shared. ProtoBot wants both ends of this range at once.

Axis 5 — Verification, and the oracle problem

Forge, Fullsend and DEX all operate on existing repositories with existing test suites. That means they can outsource the hard question — "is this correct?" — to CI. ProtoBot builds from zero, where no oracle exists, so it cannot. This is why it is the only one of the four attacking verification head-on with dual-model isolation and mutation testing. The problem is real and correctly identified. Whether the answer works is §03.

03

Project by project

ProtoBot design draft

The most intellectually ambitious of the four and the only one with no code. Its related-work survey is better than anything in the other three repositories — it has clearly read the field. Its risk is that everything hard is still marked "needs design".

Right calls
  • correct A validated, queryable spec store. ears-manager as a static Go binary, deterministic, format-agnostic, callable by agents, CI and humans alike. This is the correct lesson from both IdeaBot's leakage problem and Yegge's 605-markdown-file collapse. It is the best single decision in the document.
  • correct EARS instead of Gherkin. Well argued. Gherkin's feature/rule scaffolding is largely non-executable and exists to group tests; dropping the intermediary and generating tests straight from requirements removes a whole layer of drift.
  • correct Separating spec content from lifecycle state. Content in git via ears-manager, lifecycle in the tracker via the WMS adapter, because atomic claim needs compare-and-swap and files in git cannot provide it. Subtle and right.
  • correct Evaluability as a day-one architectural constraint, with a per-component eval table and the observation that preserved git history is itself the eval dataset. No other project in the set treats this as structural.
  • correct Naming the oracle problem. The dual-model isolation idea is the right response to the evidence it cites — measurable cheating rates in reimplementation benchmarks, and Claude inserting comments purely to satisfy string-matching assertions.
Gaps
  • critical The triage step leaks the isolation it is supposed to protect. Triage must see both Workers' output to attribute a failure. The moment it tells Worker B "the test expects 401 and you return 200", it has transmitted the test. Isolation degrades into a slower information channel across iterations rather than a barrier. The document notices the tension (Q15) but treats it as a scheduling question; it is a soundness question. Four of the open questions — 8, 9, 10 and 15 — sit on this one critical path.
  • critical The Building loop has no termination condition. "Repeat until all tests pass" — no retry cap, no budget ceiling, no blocked state, no escape hatch. Forge caps CI repair and has forge:blocked plus forge:retry. DEX has maxLoopCycles, maxBudgetUsd and an explicit cycle-failure policy. Fullsend names flapping convergence as a tracked problem. ProtoBot cites the benchmark result where a model burned ~900M tokens on the wrong architectural foundation, then designs no defence against it.
  • critical No cost model anywhere. Two Workers, N Inspectors, mutation testing on generated code, and an uncapped iteration loop is the most expensive pipeline of the four by a wide margin. Forge tracks per-ticket cost in Grafana; DEX has a spend ceiling that stops the loop. ProtoBot never mentions budget.
  • check "The difference is ceremony, not architecture" is probably false. Fullsend spent roughly thirty ADRs on exactly this boundary — per-repo versus per-org installation, dispatch routing, token minting, privilege levels, version skew — and deprecated several of its own answers along the way. The claim is an aspiration; the neighbouring project's evidence contradicts it.
  • check Security is cited, not designed. OpenShell and the Bridge/Gate pattern are named as adopted, but there is no threat model, no per-component privilege table, no injection analysis. Worse, the document itself records that IdeaBot rejected OpenShell in May 2026 over OpenShift SCC issues — flagged, unresolved, and on the critical path.
  • check The gate is in the wrong place for the stated product. A disposable demo prototype gets one early gate and full autonomy through merge; the document then concedes in Q13 that its own risk rating will likely force another checkpoint anyway. Your margin note about the prototype/bootstrap contradiction is the same tension surfacing twice.
  • check Ongoing obligations will not scale as specified. Q19 is a genuinely good catch that nobody else has named — but the proposed mechanism, filtering ubiquitous and state-driven requirements by interface and letting the Worker judge applicability, is per-work-item LLM judgement over a growing requirement set. It gets more expensive exactly as the project gets more valuable.

DEX working app

You know why it looks the way it looks, so this is the outside view: what it solves better than the other three, and where the single-player choice has a real cost.

Right calls
  • correct The timeline is the best human-control surface in the set. Forge and Fullsend give you approval gates — binary and forward-only. DEX gives you a branching DAG where one click jumps, forks or promotes. For prototyping, being able to fork at a stage and try the other direction beats approving each step. ProtoBot has nothing equivalent, and your own margin note asking for git branches per spec is exactly this feature — already built and proven.
  • correct Deterministic feature selection. The manifest is extracted once and read mechanically; the LLM is confined to a five-value decision. That is Fullsend ADR 0018's conclusion, implemented independently, without needing the failed experiment first.
  • correct Mock backend plus checkpoint replay. This is the most practical answer in the set to "how do you affordably test a non-deterministic, LLM-billed system". Fullsend needed several ADRs and a dedicated eval harness to get here. Forge's local testing requires Redis, Podman and Jira access. ProtoBot's documents never address how the Job Site gets tested at all.
  • correct No database. Git refs authoritative, JSON as cache. This is Beads' lesson without importing Beads' complexity.
  • correct The 600-LOC ceiling enforced in CI. Crude, but it is a working answer to a problem Fullsend has open as agent-compatible-code.md and nobody else has addressed at all.
Gaps
  • notable Verification is the weakest of the four. One verify stage, same trust lineage as the implementer, no independent reviewer, no dimensional fan-out. Forge and Fullsend both run adversarial review as a separate role with separate context; ProtoBot goes further still. Self-review is the weakest form, and it is the form DEX uses. This is the clearest single upgrade available.
  • check learnings.md is the pattern Beads exists to replace. An append-only markdown file that accumulates across cycles will grow past useful and degrade quietly. Fullsend tracks this as cross-run-memory.md; it is a known trap.
  • check No well-formedness gate on intent. Spec-kit gives structure but nothing equivalent to ears-manager check — no CI gate that fails when a spec is malformed or references something that does not exist. ProtoBot is right that this matters.
  • scope Single-player by construction. No sandbox, no credential isolation, no multi-tenancy — entirely coherent for a desktop app, but it means there is no layer to extend if DEX ever needs to run unattended or against someone else's repository. That would be an addition, not a configuration.

Forge production service

The most mature workflow engineering of the four — it reads like it was built by people who have operated distributed systems and been paged by them. Its own documentation is unusually honest about where it is unsound.

Right calls
  • correct Failure handling as a first-class concern. Checkpoints per ticket, resume from the failed node, dead-letter queue, exponential backoff, an explicit blocked state with a retry label. Nobody else in the set has this depth, and ProtoBot has none of it.
  • correct Cross-repo decomposition. Forge natively plans a feature across services, clients, infrastructure and docs repos, then splits it into independently reviewable repo-scoped units. DEX, Fullsend and ProtoBot all assume one repository. ProtoBot will hit this the first time it builds anything real.
  • correct Observability that answers business questions. Prometheus, Langfuse and Grafana giving cost per ticket and latency per workflow step. ProtoBot's evaluability section describes wanting roughly this; Forge already runs it.
  • correct Layered skill overrides — team defaults with project, repo and stack overrides — so teams adapt behaviour without forking the orchestrator. ProtoBot correctly identified this as the model for its Specification Toolkit.
Gaps
  • notable Documented and unfixed correctness holes. The internals doc states plainly that the deduplication service exists but is not wired into the webhook routes; that checkpoint writes and external side effects are not transactional, so a crash between them duplicates Jira comments on retry; and that per-ticket serialisation uses an in-process lock rather than a distributed one, which makes horizontal worker scaling unsound. Honest documentation, real bugs waiting.
  • notable Redis is a total single point of failure — "complete system outage; all state at risk" — with no built-in HA.
  • check Blanket network isolation. No L7 policy, so there is no way to permit package registries and documentation while blocking exfiltration. ProtoBot correctly identifies this as disqualifying for its own use case, where scaffolding from zero requires registry access.
  • check Gates pause indefinitely. No timeout, no escalation. In practice that means tickets rot silently in the approval queue.
  • scope Jira-only intake and the heaviest operational burden of the four.

Fullsend production platform

The strongest security architecture and the strongest design process in the set. Also the one whose complexity is visibly running ahead of it in one specific layer.

Right calls
  • correct Credential isolation reasoned from first principles. ADR 0017 does not argue from a detection rate; it argues that the attack is fundamentally asymmetric, so no detection rate would be sufficient, so credentials must simply not exist in the sandbox. Default is prefetch-in / post-script-out; the REST proxy with L7 policy is the documented fallback with its maintenance cost stated honestly. This is the best piece of security reasoning across all four repositories.
  • correct Unidirectional control flow. No layer may reconfigure any layer above it — with the distinction between prohibited upward control and permitted upward data drawn precisely. It buys security, portability and testability from one invariant.
  • correct Zero infrastructure. Running as a CI job removes the deployment conversation entirely. ProtoBot's stated requirement to work without a Kubernetes cluster is exactly what this already solves.
  • correct Deliberately bounded intake. Triage reads title, body and attachments — never the comment thread. Cheaper, more predictable, and it removes a large prompt-injection surface. A real insight, and cheap to copy.
  • correct ADR discipline. Frozen on acceptance, superseded rather than edited. It is why the reasoning is still legible at 80+ decisions, and it is why this repository is the most useful one to learn from.
Gaps
  • notable Intent representation is the weak flank, and they know it. Work starts from an issue body; nothing durable defines what the system is supposed to be. Fine for "fix this bug", insufficient for "build this product". It is the exact mirror of ProtoBot's strength.
  • check The distribution layer has outgrown the agent layer. Token minting, per-repo versus per-org modes, dispatch version skew, CEL triggers, layered content resolution — with several ADRs deprecating earlier ADRs in the same area. That churn is the honest signal: this boundary is much harder than it looks, and it is the same boundary ProtoBot calls "ceremony, not architecture".
  • check Per-agent sandboxes are expensive by design. ADR 0020 states the arithmetic — N agents × M concurrent tasks × a cold start each — and accepts it. Security was chosen over cost, deliberately, but the cost is real and there is no cost model published the way Forge has one.
04

ProtoBot's open questions that are already answered next door

Several items on ProtoBot's open-questions list are running in production in a sibling project. These are not research problems for ProtoBot; they are integration decisions.

Open question Already solved by The answer
Q12 — Inspector roster Fullsend Config-driven agent registration. Org or per-repo config lists the agents; the pipeline provisions them. Adding a review dimension is a config change, not a code change.
Q14 — Inspection report format Fullsend Structured, not free-form. Schema-locked JSON findings with a severity threshold, harness-level enforcement and a two-retry validation loop. Free-form would forfeit the ability to filter, deduplicate and route mechanically.
Q15 — Triage mechanism Forge A bounded loop with explicit caps, a blocked state and an operator-visible retry trigger. The shape is proven; what ProtoBot still owes is how it survives contact with dual-model isolation.
Q2 — Escalation channel Forge · Fullsend The tracker is the channel. Labels and comments carry the escalation; humans already watch that surface. No separate notification system is needed.
Q7 — Requirements storage format DEX Make git refs authoritative and treat the structured file as a rebuildable cache. Removes most of the merge-conflict pressure that makes the JSONL question feel load-bearing.
Single-player deployment Fullsend Run the pipeline as a CI job. No server, no cluster, and the same artifact works for one developer or a whole org.
Credential isolation Fullsend Adopt ADR 0017 wholesale rather than re-deriving it. The reasoning, the fallback tier and the honest cost accounting are all already written.
05

What none of them has solved

  1. Generating from zero with no oracle.

    Forge, Fullsend and DEX all work inside repositories that already have tests, so CI answers "is this correct?" for them. ProtoBot scaffolds from nothing, which is precisely why it needs dual-model isolation — and why it cannot borrow anyone's answer. This is genuinely open, and ProtoBot is the only one working on it.

  2. Triaging a surviving mutant.

    ProtoBot's own analysis is correct and uncomfortable: distinguishing an equivalent mutant from a weak test from unspecified behaviour requires knowing whether the mutated program still conforms to the spec — which is the oracle you were trying to build. Mutation testing stays useful in aggregate as a coverage signal; per-mutant routing has no mechanical answer.

  3. Knowing when to stop.

    Forge caps retries, DEX caps cycles and spend, Fullsend names flapping convergence as an open problem. All three bound the loop; none can tell you whether the loop is converging or thrashing. Bounding is not the same as knowing.

  4. Durable intent that survives the system.

    Fullsend has minimal intent and knows it. Forge's artifact chain is generated per ticket and does not accumulate into a definition of the product. DEX's specs are prose. ProtoBot's answer — a validated requirement store — is the most promising, and it is untested at any scale.

06

The short version

If ProtoBot changes three things

Bound the Building loop. Retry cap, budget ceiling, blocked state, escalation path. This is the highest-value change and the cheapest — Forge's shape can be copied directly.

Decide what triage is allowed to say. Dual-model isolation is the document's best idea and its most fragile one. Until the triage message format is specified — and specified as something that cannot carry the test's content — isolation is an intention rather than a property.

Stop re-deriving Fullsend. Credential isolation, structured findings, config-driven reviewer rosters, escalation through the tracker, and CI-as-infrastructure are all already reasoned out one directory over. Adopting them frees the design budget for the oracle problem, which is the part only ProtoBot is working on.

If DEX changes one thing

Add an independent reviewer with its own context — not a second pass by the same lineage. A read-only agent fanning out across two or three dimensions, returning structured findings, gating the stage commit. Both production systems in this set converged on that shape, and it is the one structural idea DEX is missing. Everything else it does differently, it does defensibly.

The uncomfortable summary is that ProtoBot has the best ideas and no evidence, Fullsend has the best engineering discipline and the thinnest notion of intent, Forge has the most operational maturity and the narrowest intake, and DEX has the best human-control surface and the weakest verification. None of them is wrong about the thing it chose to be good at.
