01

The one-line version

Fullsend is a dispatcher. GitHub tells it something happened. It picks exactly one robot, runs it once, and stops.

There is no brain sitting in the background watching your repository. Every robot run starts from one GitHub event: someone opened an issue, someone pushed a commit, someone added a label, someone typed a command. One event in, at most one robot out.

The state of the work lives in GitHub itself, in the labels on your issues and pull requests. The labels are the machine. Fullsend just reads them and acts.

The mental model

Think of a taxi dispatcher with a radio. Calls come in. For each call the dispatcher sends one driver, or nobody. The dispatcher never drives, and never remembers yesterday.

02

The crew

Six robots. Each one has a single job and its own GitHub identity, so you can always see in the timeline which robot did what.

Triage

Reads a new issue. Decides if it is clear enough to work on, a duplicate, blocked by something else, or just a question. Adds labels and writes a summary.

fullsend-ai-triage[bot] · reads only

Code

Takes a ready issue and writes the change. Creates a branch, runs the tests, and opens a pull request that closes the issue.

fullsend-ai-coder[bot] · writes code

Review

Reads a pull request and reviews it. It splits the work across helpers that each look at one thing: correctness, security, intent, style, documentation.

fullsend-ai-review[bot] · reads only

Fix

Reads the review and fixes what it asked for. Pushes one commit to the same branch. It is the same robot as Code, wearing a different hat.

fullsend-ai-coder[bot] · writes code

Retro

Runs after a pull request closes. Looks at the whole story and files new issues about what could work better next time.

fullsend-ai-retro[bot] · files issues

Prioritize

Scores an issue on Reach, Impact, Confidence and Effort, and writes the score onto the project board. Runs on a schedule, not on events.

fullsend-ai-prioritize[bot] · scores issues

Triage, Review and Retro cannot change your code at all. They read, and they produce a report. Only Code and Fix write, and even they never push directly from inside the robot. More on that in the guard rails.

The route map

Every event travels the same path. One workflow catches it, one step decides which robot to call, four checks can still stop it, and then one job runs.

The one that surprises people

A human review does not start the Fix robot. Only a review from fullsend-ai-review[bot] does. If you want your own review comments acted on, you must type /fs-fix yourself.

Labels are the buttons

Fullsend has no separate control panel. The labels on the issue or pull request are the control panel. There are three kinds.

Buttons that start a robot

LabelPut it onWhat happens

Lights that report a decision

These do not start anything. They tell you what a robot decided.

LabelSet byMeaning

Brakes

LabelEffect
fullsend-no-fixThe Fix robot will not run by itself on this pull request. You can still call it by hand with /fs-fix.
fullsend-fixThe opposite switch. On a pull request written by a human, the Fix robot stays quiet unless you add this label.

Remove a label and the button is un-pressed. Nothing is locked. The labels are yours.

Slash commands

You can also call a robot directly. Write the command as the first word of a comment on an issue or a pull request.

CommandWhereWhat it doesAccess needed
/fs-triageissueRuns triage again from scratchtriage
/fs-codeissueStarts the Code robot nowwrite
/fs-reviewpull requestRuns a fresh reviewtriage
/fs-fixpull requestStarts the Fix robot. You may add your own instruction after itwrite
/fs-fix-stoppull requestAdds fullsend-no-fix and stops automatic fixingwrite, or you opened the PR
/fs-retroissue or PRRuns a retrospective. You may add what to focus onwrite
/fs-prioritizeissueScores the issue on the project boardwrite

Free text is the most useful feature here

/fs-fix and /fs-retro accept anything you write after the command. That text goes straight to the robot and outranks the review it would otherwise follow. On pull request 61 this was used to point the Fix robot at inline comments it cannot see on its own.

07

The review and fix loop

This is where most of the work and most of the money goes. Review reads the pull request. If it wants changes, Fix makes them and pushes a commit. The push starts a new review. Round and round.

Two things worth knowing

  • The Fix robot reads the summary of a review, not your inline comments on single lines. If your point is in an inline comment, paste it into a /fs-fix comment.
  • Every new push cancels the review that is still running on the old commit. That is why the run list is full of cancelled reviews. It is normal.

Six review runs and five fix runs, 33.57 dollars of model time in total, over about 19 hours of wall clock. Two of those runs were cancelled by a new push, and one review failed its own output check.

09

The guard rails

Six things stop a robot from doing damage. They are worth knowing because they explain why runs sometimes do nothing.

The robot has no network

Agents run in a sandbox. They can reach the model and the GitHub API and nothing else. No pastebins, no gists, no random web pages.

The robot cannot push

The robot writes a report. A script outside the sandbox reads it, scans for secrets, and only then pushes or comments.

Short-lived keys

Each role gets its own GitHub App token, minted fresh for that one run and scoped to this repo. No long-lived secret is stored in the repository.

Fork pull requests cannot trigger Fix

If the branch lives in someone else's copy of the repo, the Fix robot is blocked outright.

Round limits

Five automatic fix rounds per pull request. Ten in total. The warning label goes on before the limit is reached.

One master switch

Set kill_switch: true in .fullsend/config.yaml and every robot stops, immediately, for the whole repository.

Your normal GitHub rules still apply on top of all this. Branch protection, required checks and CODEOWNERS work exactly as before. A robot cannot merge past them.

10

What ProtoBot changed

Fullsend ships with defaults. ProtoBot changed five of them. These are the differences that will confuse you if you read the general documentation.

SettingDefaultOn ProtoBotWhy it matters to you
Triage hands off to Code Yes, for bugs, docs and performance issues Off Triage always stops at triaged. A person must add ready-to-code or type /fs-code. Nothing gets built by surprise.
Renovate pull requests Reviewed like any other Skipped Dependency bumps do not burn review money.
Start comments Posted Turned off, replaced by an emoji reaction Fewer notifications. A robot that is working shows as a reaction, not a comment.
Where robots may file issues This repo only Also fullsend-ai/fullsend and fullsend-ai/agents Retro and Triage can file upstream bugs against Fullsend itself.
CodeRabbit reviews Ignores App bots A small local workflow asks it to review anyway Robot pull requests get the same second opinion as human ones.

Everything else is stock. All six roles are on, the runtime is Claude, and the version is pinned to Fullsend v0.40.0.

Cheat sheet

Make a robot build this issueAdd ready-to-code, or comment /fs-code.
Re-run triage after you added detailsComment /fs-triage. Editing the issue body also works.
Get a fresh reviewPush a commit, or comment /fs-review.
Make the robot act on your reviewComment /fs-fix and paste your points. A plain human review does not start it.
Stop the robot pushing to your branchComment /fs-fix-stop. Undo it by removing fullsend-no-fix.
Understand why nothing happenedOpen the Actions tab. Look at the newest fullsend run. The route step logs the stage it picked, or says no stage matched.
Know what a run costRead the last comment the robot posted. It carries the run time, the model and the price.
Stop everything right nowSet kill_switch: true in .fullsend/config.yaml on the main branch.
