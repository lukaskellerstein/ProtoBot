01

What Fullsend is

Fullsend turns GitHub events into single, sandboxed agent runs. It has no server, no queue and no memory. GitHub itself is the coordinator, and the labels on issues and pull requests are the state.

Fullsend defines a five-layer execution stack. Control flows strictly downward. No layer can configure or influence a layer above it, which is the structural rule the whole security story rests on.

LayerJobWhat it is on ProtoBot
Dispatch and coordinationTurn an event into one agent task.github/workflows/fullsend.yaml calling the upstream reusable-dispatch.yml
InfrastructureProvide the computeGitHub Actions, runner image ubuntu-24.04
SandboxContain the agentOpenShell container, network allowed per binary and per endpoint
HarnessAssemble prompt, skills, tools, scriptsYAML in fullsend-ai/agents, layered with .fullsend/harness/*.yaml
RuntimeRun the modelClaude Code, Opus through Vertex AI in GCP project it-gcp-octo-fullsend

Three things sit beside the stack rather than in it: the policy store (what agents may do), the identity provider (the token mint that issues per-role GitHub App tokens), and observability (OpenTelemetry traces plus the status comments you see on each issue).

Per-repo installation

ProtoBot uses per-repo installation mode. Everything lives in this repository: .fullsend/config.yaml, .fullsend/harness/, and the shim workflow. There is no separate redhat-et/.fullsend config repository. Org-level installation is deprecated upstream, so ignore any documentation that describes it.

The six agents

Each agent is a harness file plus a GitHub App identity plus a JSON output schema. All six roles are enabled on ProtoBot.

AgentRole keyApp identityWrites?Output
Triagetriagefullsend-ai-triage[bot]NoStructured triage decision. The post-script applies labels and posts the summary.
Codecoderfullsend-ai-coder[bot]YesLocal commits. The post-script pushes the branch and opens the pull request.
Reviewreviewfullsend-ai-review[bot]NoStructured review result. The post-script posts the review and applies outcome labels.
Fixcoderfullsend-ai-coder[bot]YesOne commit. The post-script pushes it and posts a summary comment.
Retroretrofullsend-ai-retro[bot]NoImprovement proposals. The post-script files them as issues labelled ready-for-triage.

Identity trap

Fix and Code share one identity. A commit or comment from fullsend-ai-coder[bot] can be either agent. Read the comment body: the fix agent labels its summaries "Fix agent — iteration N".

Harness shape

Every agent harness declares the same fields. The triage harness at v0.40.0, for example, sets model: opus, effort: high, a pinned sandbox image digest, policy: policies/base.yaml, a Vertex AI provider, pre_script and post_script, a validation loop with max_iterations: 2, and timeout_minutes: 10.

A repository overrides a harness by composition, not by copying. ProtoBot's .fullsend/harness/triage.yaml is five lines: a base: URL pinned to v0.40.0 with a SHA-256 integrity hash, plus the one environment variable it wants to change.

03

The dispatch chain

From event to job

The shim workflow in ProtoBot subscribes to four event types and forwards them all to one upstream reusable workflow, which does the routing and then runs the stage job inline.

# .github/workflows/fullsend.yaml  (managed by fullsend, do not edit)
on:
  issues:              types: [opened, edited, labeled]
  issue_comment:       types: [created]
  pull_request_target: types: [opened, synchronize, ready_for_review, closed, labeled, unlabeled]
  pull_request_review: types: [submitted]

jobs:
  dispatch:
    uses: fullsend-ai/fullsend/.github/workflows/reusable-dispatch.yml@2a10349  # v0.40.0
  stop-fix:            # separate job, handles /fs-fix-stop only

The job-level condition drops three classes of event before any compute is spent: anything on the fullsend/scaffold-install branch, any comment from a bot, and Renovate pull requests on the actions that would otherwise start a review.

Inside reusable-dispatch.yml there is one route job and one job per stage. Only the job whose name matches the routed stage runs. Adding a stage upstream needs no change in ProtoBot.

What the route job does, in order

  1. Sparse-checkout of .fullsend/config.yaml only, pinned to the base branch SHA on pull request events. No pull request code is fetched.
  2. Run the routing script. It reads the event, the added label, the comment body and the actor, calls the collaborator permission API where needed, and sets exactly one stage or an empty string.
  3. Validate the stage name and the trigger source string against a strict pattern.
  4. Check the kill switch: kill_switch: true in config fails the run immediately.
  5. Validate the shape of the agents: block: it must be a list, disabled entries need a name, enabled entries need a source or a tuning field, and names must be unique.
  6. Check the role is listed in roles:. Stages code and fix both map to the role coder.
  7. Check the agent is not disabled by agents[].enabled: false.
  8. For stage code only: query GitHub GraphQL for pull requests that actually close the issue through a Fixes, Closes or Resolves keyword. If an open one exists, skip. Pull requests authored by the coder bot are excluded from this check so it can re-dispatch on its own branch.
  9. Build the event payload: issue, pull request head and base, and the comment body truncated to 4096 bytes.

What one agent run looks like

Every stage job has the same five phases. The trust boundary is the sandbox wall: nothing inside it can write to GitHub.

Event: pull_request_review

This is the one rule with a compound condition, and it is the rule people misread. Every clause must hold.

#Clause
1The review state is changes_requested
2The reviewer is fullsend-ai-review[bot] or <org>-review[bot]. A human review never matches.
3The pull request head repository equals the base repository. Fork pull requests are blocked, and an unknown answer fails closed.
4The pull request does not carry fullsend-no-fix
5Either the pull request author is a bot, or the pull request carries fullsend-fix and its author has write permission

All five true gives stage fix, with the review bot recorded as the trigger source.

Event: issue_comment

The first whitespace-delimited word of the first line is taken as the command, with trailing punctuation stripped. Bot comments are filtered out at the job level.

How permission is resolved

Not from author_association. The route step calls repos/{owner}/{repo}/collaborators/{user}/permission and accepts admin, maintain or write; triage is accepted only where the table says triage-level is enough. The API resolves organisation membership even when it is private. If the call fails, the answer is no.

Labels as the state machine

Fullsend keeps no state of its own. The labels are the state, GitHub stores them, and agents hand off to each other by applying one. That is why a bot applying a label re-enters the router as a fresh event.

Every label, and who reads it

LabelApplied byRead by the router?Effect
ready-for-triageRetro post-script, or a humanYes, on issuesDispatches triage, no permission test
ready-to-codeA human on ProtoBot. Triage post-script elsewhere.Yes, on issuesDispatches code, if the labeller is a bot or has write
ready-for-reviewCode post-script after pushingYes, on pull requestsDispatches review
fullsend-no-fix/fs-fix-stopYes, in the fix ruleBlocks automatic fix runs. Manual /fs-fix still works.
fullsend-fixA humanYes, in the fix ruleOpts a human-authored pull request into automatic fixing
triagedTriage post-scriptNoClear issue, waiting on human prioritisation

duplicateTriage post-scriptNoIssue closed, canonical issue linked
ready-for-mergeReview post-scriptNoApproved at that exact head SHA. Removed on the next round.
requires-manual-reviewReview post-scriptNoThe agent could not confidently approve or reject
rejectedReview post-scriptNoRejected, and the pull request was closed
risk/low risk/moderateReview post-scriptNoThe risk score, with its reasoning in a details block

Stale outcome labels from an earlier review round are removed before the new one is applied, so ready-for-merge always describes the current head commit and never an older one.

Slash commands

Commands are parsed from the first word of the first line. They are the manual override for every automatic path, and two of them accept free text.

CommandArgumentsNotes
/fs-triagenoneRe-evaluates the issue from current content and any prior triage analysis. Reopens a closed issue.
/fs-codeoptional --forceIssues only. The open-pull-request guard still applies unless forced.
/fs-reviewnoneQueues a review round against the current head SHA.
/fs-fixfree text, up to 10,000 bytesThe text becomes HUMAN_INSTRUCTION and outranks the review body. Cancels any fix run already in flight on this pull request.
/fs-fix-stopnoneHandled by a separate job in the shim, not by the router. Adds the label and posts a confirmation.
/fs-retrofree textThe text is passed as high-signal direction about what to analyse.
/fs-prioritizenoneScores the issue and writes to the project board.

07

The review and fix loop

This loop consumes 47 percent of all runs on ProtoBot and 58 percent of the spend. Understanding its exits is the highest-value part of this page.

What one review run actually does

  1. The pre-script fetches pull request metadata and any prior review.
  2. Inside the sandbox the agent runs the pr-review orchestrator skill. The orchestrator triages the change, then dispatches sub-agents in parallel, one per dimension: correctness, security, intent and coherence, style and conventions, documentation currency, and optionally cross-repo contracts.
  3. The orchestrator collects the sub-agent findings, removes duplicates, and runs pull-request-level checks for scope authorisation and protected paths.
  4. It emits one JSON review result, which is validated against the schema with up to 2 retries.
  5. The post-script posts the review, the risk assessment, and the outcome label.

Findings below the REVIEW_FINDING_SEVERITY_THRESHOLD are dropped from both the narrative and the inline comments. The default is low, so on ProtoBot you see everything above informational.

The four outcomes

OutcomeLabel appliedWhat happens next
Approveready-for-mergeLoop ends. Merge under your normal governance.
Request changesNoneThe pull_request_review event dispatches the fix agent directly.
Cannot deciderequires-manual-reviewA human must judge it.
RejectrejectedThe post-script closes the pull request.

Why the run list is full of cancellations

20 of 109 review runs on ProtoBot were cancelled. That is the concurrency group doing its job, not a fault. The cancelled run was reviewing a commit that no longer matters. On pull request 61 you can see this at 21:21 and again at 13:46.

The guard rails

Fullsend's threat model ranks external injection above insider risk, above drift, above supply chain. These controls follow that order.

The pull_request_target design

The shim runs on pull_request_target, so GitHub always executes the copy of the workflow on the base branch. A contributor cannot edit the workflow in their pull request and have their version run. The shim itself never checks out pull request code, and the router's checkout is a sparse checkout of .fullsend/config.yaml pinned to the base SHA. That is what makes it safe to hand this workflow write permissions.

Credentials

  • No long-lived GitHub secret is stored in the repository. The job exchanges its OIDC token at the token mint for a GitHub App installation token scoped to one role and this repository.
  • Each role is a separate GitHub App with its own permission set. The coder token has no workflow write permission, so a code agent cannot modify files under .github/workflows/.
  • The read-only token enters the sandbox. The read-write token stays on the runner.
  • Model credentials never enter the sandbox at all. They are delivered through OpenShell provider profiles with layer-7 endpoint allowlists.

Sandbox

  • Network is granted per provider profile and enforced per binary: Vertex AI for the model process, the GitHub API for gh and git, package registries for package managers. Everything else is refused.
  • A context scan runs before the agent starts, checking AGENTS.md, CLAUDE.md and similar files for prompt injection.
  • allowed_remote_resources in config limits which URLs a harness may compose from. ProtoBot allows only the two fullsend-ai raw content paths.

Output and loop control

  • Every agent output is validated against a JSON schema on the host, with 2 retries. An unvalidated result is never published.
  • A run killed at timeout_minutes is not retried. It ends with a timeout error.
  • Fix rounds are capped at 5 automatic and 10 total per pull request.
  • Fork pull requests cannot trigger the fix agent, and an unknown fork status fails closed.
  • kill_switch: true in .fullsend/config.yaml fails every dispatch at the router.

Repository governance is unchanged by all of this. Branch protection, required checks and CODEOWNERS apply to agent pull requests exactly as they apply to yours. Trust comes from repository permissions, not from which bot identity holds the token.

The five deliberate differences from stock

Repository context that shapes every agent

  • AGENTS.md is read by all six agents. ProtoBot's version defines the specification document hierarchy and the rules for changing anything under docs/. It also instructs review agents to check cross-document coverage.
  • .agents/skills/ holds three local skills: pull-request, rebase-pr and review-pr. .claude/skills is a symlink to that directory, so local Claude Code sessions and Fullsend agents load the same set.
  • The version is pinned. Both the shim and prioritize.yml call the upstream reusable workflows at commit 2a10349, tag v0.40.0. Renovate proposes the bump when a new tag ships.

Where to look when it goes wrong

Nothing happened after an eventActions tab → newest fullsend run → the Route job. The log prints either "Routed to stage: X" or "No stage matched — skipping dispatch". Then check the notices for a role, agent or open-pull-request skip.
A run finished but nothing was postedThe schema check failed after 2 iterations, or the post-script failed. The completion comment names the reason.
A run says CancelledNormal. A newer event replaced it in the same concurrency group.
The fix agent ignored your reviewHuman reviews never trigger it, and inline comments are never read. Comment /fs-fix with your points pasted in.
The fix agent stopped by itselfLook for needs-human or fullsend-no-fix on the pull request.
You need the transcript of a runThe run uploads a JSONL transcript as a workflow artifact. The analyze-transcript and replay-session skills in the fullsend checkout read them.
Change what an agent doesRepo-wide rules go in AGENTS.md. Per-task behaviour goes in a skill under .agents/skills/. Model, effort, image and policy go in a harness override under .fullsend/harness/.
Stop everythingSet kill_switch: true in .fullsend/config.yaml on the default branch. The router fails every dispatch until you unset it.
