Before you start

You work in three places. Each one has its own job, and each one is opened in its own way. The first line of every Claude session, the Worktree guard line, tells you which place you are in. Read it.

Three skills you do not use

pull-request, rebase-pr and review-pr are upstream's. They describe the maintainer's own flow: a draft PR, CodeRabbit replies, auto-merge. Since 10 September 2026 skillOverrides in .claude/settings.json hides all three, so no session lists them, in the main checkout or in a worktree. The files stay in the repo, untouched: a private commit that deletes them conflicts on every upstream edit, and a worktree is cut from upstream/main and would get them back anyway. The private skills above replace them.

One-time setup

Check these once. Every skill that talks to GitHub needs the first one.

gh auth status                 # must say "Logged in". If not: gh auth login -h github.com
git remote -v                  # origin = lukaskellerstein/ProtoBot, upstream = redhat-et/protobot

uvx runs pre-commit on demand. The skills and every code block on this page call it that way. Do not run pre-commit install: a git hook would block every commit on skillsaw, see step 4 of section 1.

01

Start work on an issue

Session a terminal in ProtoBot/, then claude -w lukas/<n>-<slug>

  1. Catch up the fork first

    in ProtoBot/ — claude --no-worktree — optional, two minutes

    Type /sync-fork. It fetches, checks that every private commit touches only private paths, rebases fork main on upstream/main, pushes with a lease, and lists worktrees that are behind. By hand:

    git fetch upstream --prune
git rebase upstream/main
git push --force-with-lease origin main

    The worktree hook fetches upstream/main on its own, so the new branch is fresh even without this step. This step keeps fork main and your notes current. Skip it when you are in a hurry.

  2. Name the branch

    The name is lukas/<issue number>-<short slug>, lowercase, words joined with dashes. The live example is lukas/34-git-integration. The name is the branch, the worktree directory and the PR head, all at once.

  3. Start the worktree session

    from any directory inside the repo

    cd ~/Projects/Github/lukaskellerstein/ProtoBot
claude -w lukas/34-git-integration

    The WorktreeCreate hook does the rest:

    • fetches upstream/main
    • creates .worktrees/lukas/34-git-integration on a new branch lukas/34-git-integration, cut from upstream/main, never from fork main
    • copies .claude/settings.json, hooks/, rules/ and CLAUDE.md into it, so the guard and the sandbox work there
    • links the five worktree skills to the main checkout

    The first line of the session must say Worktree guard: worktree …/.worktrees/lukas/34-git-integration. If it says MAIN checkout, you forgot -w. Exit and start again.

    Come back tomorrow

    The same command, claude -w lukas/34-git-integration, adopts the existing worktree. If the directory is gone but the branch exists, the hook checks the branch out again. Two sessions can share one worktree. Re-read a file before you edit it.

  4. Set up the worktree

    in the worktree

    A fresh worktree has no gitignored files. This project is documents and scripts, and CI runs only pre-commit, so there is nothing to install. Warm up the hooks once:

    SKIP=skillsaw uvx pre-commit run --all-files     # the first run downloads the hooks, about a minute

    Prefix every local pre-commit run with SKIP=skillsaw. That hook fails locally today: in the main checkout on two warnings in private files, in a worktree also on the linked skills, which the tool does not follow. CI runs it on the real tree, where it passes. There is no git hook, so a plain git commit needs no prefix.

  5. Build the change

    in the worktree

    Ask Claude for the change. Which skill runs depends on what the change touches. Most changes need none of them.

    The changeRunWhen
    Touches no file under docs/: scripts, workflows, README, skillsnone—
    Creates or edits a document under docs//spec-doc docs/<path>, once per changed documentBefore the last commit. Again if a sibling document changed under you. The review bot runs the same check, so what it would find is cheaper found here.
    Makes a decision: resolves a question in open-questions.md, changes what an accepted ADR decided, or the issue asks for a decision record/adrBefore the documents that depend on the decision. It runs /spec-doc on the record itself, so only the other documents you touched need their own run.
    Any change, while you buildnever /fullsendIt is a reference, not a step. Read it in section 3 or section 5, when you are about to touch a label or send a /fs- command. The PR skills read it themselves.

    Decision or specification? A decision says "we do X, not Y, because Z" about a question the hierarchy calls open. A specification says how a thing works or what it must satisfy: a contract, a component design, a flow. The first is an ADR. The second is a document under docs/, and /spec-doc is its check. When in doubt, it is a specification.

    Claude edits. You commit. Before every commit:

    SKIP=skillsaw uvx pre-commit run --all-files
git add -A
git commit -m "docs(#34): add git integration design"

    The message is <type>(#<issue>): <summary>, the same style the PR title will use. AGENTS.md requires every pre-commit check green before a commit.

  6. Check before the PR

    in the worktree

    git branch --show-current                # lukas/34-git-integration
git status --short                       # prints nothing
git log --oneline upstream/main..HEAD    # only your commits, no "lukas-notes", no "new skills"

    If the log shows a private commit, the branch was cut from the wrong base. Section 6 has the fix. Then go to section 2.

Several issues at once

One worktree each. Open another terminal and run claude -w lukas/35-other-thing. Git refuses one branch in two places, so the sessions cannot collide. They share .git, so a fetch in one is a fetch for all.

02

Open the pull request

Session the worktree of the branch

  1. Get the tree clean

    in the worktree

    git status --short must print nothing. Commit or stash. Claude will not commit for you, and /pr-create stops on a dirty tree.

  2. Type /pr-create

    in the worktree

    It runs these in order and stops on the first failure with the fix:

    1. Checks: the branch is lukas/…, the tree is clean, and no private file is in the diff (lukas/, .claude/, the private skills).
    2. git fetch upstream --prune, git rebase upstream/main, SKIP=skillsaw uvx pre-commit run --all-files. Nothing goes out red.
    3. git push -u origin lukas/<slug> — once, to the fork. Never to upstream.
    4. Opens the PR against redhat-et/protobot, base main, head lukaskellerstein:lukas/<slug>. Title <type>(#<issue>): <summary>. Body: what changed, why, how it was tested, then Closes #<issue>. Not a draft. No labels.
    5. Waits for CI with gh pr checks --watch, reports the URL and the result, and stops.

    By hand, if you want to see it:

    git fetch upstream --prune && git rebase upstream/main
SKIP=skillsaw uvx pre-commit run --all-files
git push -u origin lukas/34-git-integration
gh pr create --repo redhat-et/protobot --base main \
  --head lukaskellerstein:lukas/34-git-integration \
  --title "docs(#34): add git integration design" --body-file body.md
gh pr checks <N> --repo redhat-et/protobot --watch

  3. Write down the PR number, then wait

    on GitHub

    The review bot starts the moment the PR opens. It needs 30 to 45 minutes and costs 3 to 8 dollars. It posts a sticky comment, a formal review that says changes requested or approved, and labels such as ready-for-merge or risk/low.

    The fix bot never runs on a PR from the fork. Your PR is one. So nobody pushes to your branch but you.

    Do not push again yet

    Every push starts a new review run and cancels the one still running. Wait for the review, then go to section 3.

Protected paths

If the diff touches .github/, .pre-commit-config.yaml, AGENTS.md, CLAUDE.md or another path on the Fullsend protected list, the bot never approves on its own. Name the issue that authorizes the change in the PR body. A maintainer must approve either way, so this changes nothing in the process, only in the bot's verdict.

03

Answer the review on your PR

Session the worktree of the PR branch. Gone? claude -w lukas/<slug> checks the branch out again.

This is a loop. One round is: the review lands, you run the skill, it pushes once, the bot reviews again. The skill has one stop in the middle, and it knows when the loop is over.

  1. Wait until the round has landed

    on GitHub

    Best: start when the bot review is in and no run is still going. One round then answers everything at once. The bot's last status comment says Finished Review. If a human also reviewed, wait for both.

  2. Type /pr-update N stops once

    in the worktree — N is the PR number

    Step 1, collect: the PR state, CI, every unresolved thread, bot findings that have no thread, human reviews, and how far the branch is behind upstream/main.

    Step 2, judge: writes .reviews/pr-N/update-<round>.html and stops. Open that file in the browser.

  3. Read the report, then say yes

    in the browser, then in the session

    The table has one row per finding: ID, source, file:line, the claim, a verdict, importance, the planned action.

    VerdictMeansReply the skill will post
    validright, and worth a changeFixed in <sha>: …
    donethe head already has itAlready in <sha>: …
    not-validwrong, or the change costs more than it givesNot changed: <reason>
    questiona human asked somethingthe answer

    Disagree with a verdict? Say so. Claude edits the report and stops again. A plain yes is the go, and it covers the commit and the push.

    From round 3 the skill tightens: only human findings and bot findings of severity high or critical are fixed. The rest get Not changed: Round 3: style only, not worth another review run. The report says when this is in force.

  4. On yes, the skill does the round

    in the worktree and on GitHub

    1. Makes the changes the report lists.
    2. If the branch is a day or more behind upstream/main, or has a conflict: git fetch upstream && git rebase upstream/main.
    3. SKIP=skillsaw uvx pre-commit run --all-files. Nothing goes out red.
    4. One commit: <type>(#<issue>): address review round <k>. This is the one place Claude commits, on your yes.
    5. Replies in every thread with the words from the report, then resolves it. All of them, not-valid included. Bot findings without a thread get one top-level comment.
    6. Pushes once. --force-with-lease after a rebase, plain push otherwise.
    7. If a human has an open changes requested, asks that person for a re-review. A push never clears it. Only they can.
    8. Writes the round into .reviews/pr-N/state.json and reports.

  5. Wait for the next review, then decide

    on GitHub, 30 to 45 minutes

    What came backDo
    The bot approved (ready-for-merge) and no human thread is openStop. Ask a maintainer for the approval. Section 4.
    Round 3 or later, and only bot style findingsStop. Do not run the skill again. Ask a maintainer for the approval and say the bot's remaining findings are answered in the threads.
    A human requested changesRead their comments. Then /pr-update N again.
    The bot requested changes, round 1 or 2/pr-update N again.
Never on your own PR

No /fs-fix, no /fs-review, no labels. The fix bot is refused on a fork PR, and the review bot already runs on every push. Claude is the fixer here. One push per round is the whole cost control.

04

Merge

Session GitHub, then claude --no-worktree for the clean-up

Merging is a click on GitHub. The part that takes time is meeting the rules on upstream main.

Rule on upstream mainWhat it means for you
One approval from the team redhat-et/sdlc-maintainersYou are on the team. A self-approval does not count, so your own PR needs a colleague.
The check CI Workflow - Success must passThat is pre-commit on the PR head. /pr-create and /pr-update keep it green.
The merge goes through the merge queueThe button says Merge when ready. The queue runs CI once more and merges.
An approval survives later pushesA commit pushed after the approval merges under it. Good for a rebase. Dangerous on a bot PR, see B below.
Bot labels are lights, not gatesready-for-merge from the bot does not merge anything. A human approval does.

A. Your own PR

  1. Get the approval

    on GitHub

    Request a reviewer from the team on the PR page, or:

    gh pr edit <N> --repo redhat-et/protobot --add-reviewer <login>

    Then tell the person. A review request alone is easy to miss.

  2. Check the PR page

    on GitHub

    • The approval is there and not dismissed.
    • CI Workflow - Success is green.
    • No conflicts. If the page says This branch has conflicts or out of date, do section 6 first. The approval survives the push, but one more bot review run follows.

  3. Click Merge when ready

    on GitHub

    The PR enters the merge queue, CI runs once more, and the queue merges it. From the terminal, gh pr merge <N> --repo redhat-et/protobot adds the PR to the queue in the same way. The linked issue closes if the body said Closes #<issue>.

    The retro bot runs by itself on every merge and files follow-up issues labelled ready-for-triage. Nothing to do. It costs money, and only the kill switch stops it.

  4. Clean up

    exit the worktree session, then claude --no-worktree in ProtoBot/

    When you exit the worktree session, pick remove. It deletes the directory and keeps the branch. Then in the main checkout:

    1. /prune — shows a plan: worktrees and branches whose PR merged, the fork branch, .reviews/pr-N/, and review worktrees pr/<N> whose PR merged or closed. Deletes on your yes.
    2. /sync-fork — fork main now contains your merged commit, on top of the private layer.

    By hand:

    git worktree remove .worktrees/lukas/34-git-integration
git branch -D lukas/34-git-integration
git push origin --delete lukas/34-git-integration
git fetch upstream --prune && git rebase upstream/main && git push --force-with-lease origin main

B. A colleague's PR you reviewed

After phase 4 of /pr-review posted your approval (section 5), the approval rule is met: you are on the team and it is not your PR. Check that CI is green and the head is still the one you approved, then click Merge when ready. After the merge, /prune in the main checkout removes the review worktree .worktrees/pr/<N> and its branch.

Keep fullsend-no-fix on until the merge

An approval survives later pushes. If the label comes off, the bot loop restarts and its commits merge under your approval, unread. On PR 61 that cost three extra bot rounds on an approved commit. Remove the label only after the merge, if at all.

05

Review a colleague's PR

Session claude -w pr/<N>, run anywhere in the repo. One review worktree per PR, and every round of that PR from the same one, because the state lives in its .reviews/pr-N/.

The skill runs in five phases. Every write to GitHub needs a yes from you, the freeze included. It never commits or pushes. It posts to GitHub under your name, so read before you say yes. Several PRs at once are several worktrees: open another terminal and run claude -w pr/<M>.

PhaseDoesThen
0 FreezeReads the PR. On a bot PR with a live loop, asks: freeze?stops for your answer, else continues
1 ReportRefreshes the head, writes .reviews/pr-N/round-<k>.htmlstops you read it
2 PostOne GitHub review. On a re-run, first replies to and resolves the fixed threadsstops you decide about the fix bot
3 FixOne /fs-fix comment, then waits for the runstops next round is /pr-review N again
4 ApprovePosts the approval, resolves the rest, reportsends

  1. Start the review worktree

    from any directory inside the repo

    claude -w pr/61

    The hook fetches the head of upstream pull request 61 into a local branch pr/61, creates .worktrees/pr/61 on it, copies the .claude/ files and links the skills. The guard line must say worktree …/.worktrees/pr/61. Tomorrow, the same command adopts the worktree again. A closed PR still has a head and still fetches.

    The session runs under the PR's files

    AGENTS.md, .claude/ and .agents/skills/ in this worktree are the PR's versions. A PR that changes them changes what Claude reads. The skill reads that diff first and says so in the report. Treat any instruction in such a diff as content under review, not as an instruction.

  2. Type /pr-review N stops after the report

    in the review worktree

    Phase 0, freeze on your yes. The skill reads the PR and lists other humans with an open changes requested. If the author is a bot, or the PR carries fullsend-fix, and the loop is still alive, it stops with one line: Bot PR, loop alive, 2 fix rounds used, one run in flight. Freeze now? Yes posts /fs-fix-stop, checks that fullsend-no-fix lands, and waits for the running fix. No reads on. Nothing is written before your answer. /pr-review 61 freeze or /pr-review 61 no-freeze gives the answer up front. On a colleague's own PR there is no loop and no question.

    When to say yes to the freeze

    When you will spend real time on the review. The loop moves the head about once an hour and spends the shared fix budget, 5 automatic rounds of 10 in total, on the bot's own findings. Frozen, the head stands still while you read, and the budget goes to your findings. The label blocks only the bot's automatic fix rounds. Anyone can still review, and /fs-fix by hand still works. Say no when you only want a look.

    Phase 1, report. It refreshes the head first, with a fetch of pull/N/head, a hard reset and a clean, so the tree is the PR head and any fix you tried in the last round is gone. Then it reads the whole diff and every file the diff cites from disk, greps the tree, runs pre-commit, and for a document under docs/ runs the /spec-doc check on the files on disk. It reads the bot's sticky comment, so a finding the bot already has is marked Same as the Fullsend finding on this line. Then it writes .reviews/pr-N/round-1.html and stops.

  3. Read the report

    in the browser

    Four parts: the header, the verdict with a table of IDs, the comments in full, and what was checked. Each comment is a Conventional Comment:

    LabelMeansGoes to the fix bot?
    issue (blocking)must change before approvalyes
    issue (non-blocking)should changeyes
    todo, chorea small taskyes
    suggestiona better way, author decidesonly the ones you name
    questionyou need an answernever. A question needs a person
    nitpick, praise, thought, noteno actionnever

    Change what you disagree with. Claude rewrites the report and stops again. A plain yes, post it or agree moves to phase 2. Silence is not a yes.

  4. Say yes: one review is posted

    on GitHub

    Phase 2 first checks that the head on GitHub is still the one in the report. If the loop moved it, you get a fresh report and another stop. Then it posts one review with one inline comment per finding. The state is changes requested when a comment blocks, else comment. It never approves here. Then it stops and asks: does the fix bot run?

  5. Decide about the fix bot

    on GitHub

    Same-repo PR, the usual case for a bot PR on branch agent/…: say yes. Phase 3 posts one /fs-fix comment that names the IDs to handle and tells the bot how to fetch the inline comments, because the bot cannot read them on its own. It polls for Finished Fix, reads the bot's Fixed and Disagreed lists, and stops.

    PR from a fork, a colleague's own branch on their fork: the fix bot is refused. Tell the author the review is there. They fix, they push, you re-review.

    Your own review never wakes the fix bot. Only the bot's own verdict or a /fs-fix does. The bot reads only the text after /fs-fix and the bot's latest review body. Never two /fs-fix at once. Caps: 5 bot rounds, 10 in total.

  6. Next round: /pr-review N again

    in the review worktree, the same one as round 1

    The report now has three parts in this order: fixed, still open with what is still missing, new. IDs continue where they stopped. On your yes, phase 2 first replies Fixed in <sha> in every fixed thread and resolves it, then posts the new round as one review. A thread the bot disagreed with needs your words: it asks you.

    Repeat until nothing blocks.

  7. Approve, by name

    in the review worktree

    Say approve PR N. Phase 4 checks that the head you read is still the head on GitHub, puts fullsend-no-fix on if it is not yet there, posts an approval that names the SHA, resolves your fixed threads, and leaves the label on. It says why in the report. Then section 4 B.

    When you exit the session, pick keep. The worktree holds the reports and the state, and the PR is not merged yet. After the merge, /prune in the main checkout removes it and its branch.

By hand, when you need one command

REPO=redhat-et/protobot; PR=<N>
gh pr comment "$PR" --repo "$REPO" --body '/fs-fix-stop'        # freeze the loop. Whole comment, nothing after it
gh pr comment "$PR" --repo "$REPO" --body-file fs-fix.md       # first line starts with /fs-fix, your instructions after
gh pr view "$PR" --repo "$REPO" --json labels,reviewDecision   # did the label land, what is the state
gh pr review "$PR" --repo "$REPO" --approve --body "Approved at <sha>."

A /fs- command is read only as the first word of a new top-level comment. Not in a thread reply, not in a review body, not in an edit. A command you may not send fails silently, so check the label, not the exit code. The full list of gh commands, thread queries included, is in /fullsend.

06

Rebase your PR, and take upstream changes

Session the worktree of the PR branch

Rebase when you must, not every day. Each rebase is a push, and each push is one bot review run. Reasons to rebase now:

  • The PR page says conflicts or out of date.
  • A change you depend on merged upstream.
  • CI or pre-commit changed on main and your head fails it.
  • The branch is a day or more behind: git fetch upstream && git rev-list --count HEAD..upstream/main is large.

Option A — let /pr-update N do it

When comments are waiting anyway, this is the cheaper route. The skill rebases when the branch is a day or more behind or has a conflict, and its one push carries the rebase and the fixes. One review run instead of two.

Option B — by hand

  1. Fetch and rebase

    in the worktree, tree clean

    git fetch upstream --prune
git rebase upstream/main

    A conflict stops the rebase and git status lists the files. For each one: edit, then git add <file>, then git rebase --continue. To give up: git rebase --abort puts the branch back as it was.

  2. Check and test

    in the worktree

    SKIP=skillsaw uvx pre-commit run --all-files
git merge-base --is-ancestor upstream/main HEAD && echo "on top of upstream"
git log --oneline upstream/main..HEAD          # only your commits

  3. Push with a lease

    in the worktree

    git push --force-with-lease

    The lease refuses the push if something else moved your branch on the fork. Nobody should. If it is refused, git fetch origin and look at git log HEAD..origin/lukas/<slug> before you push again. Never a plain --force.

    The push starts a bot review run. An existing human approval survives it.

Rebase, never merge

Do not git merge upstream/main into the branch. The repository convention is a rebase, and a merge commit puts upstream's history into your PR's commit list. Upstream's rebase-pr skill is hidden by skillOverrides. It described the generic process, and its first step created a worktree, which your rules forbid. Use the commands above, or option A.

The PR diff shows lukas/ or .claude/

The branch was cut from fork main, not from upstream/main. The private commits come first in the log. Move only your commits:

git log --oneline upstream/main..HEAD            # private commits first, then yours
git rebase --onto upstream/main <sha of the last private commit>
git push --force-with-lease

Do not use origin/main as the cut point. It moves with every /sync-fork, and then the private commits ride along.

The fork's main is behind

That is a separate thing. Worktrees never branch from fork main, so an old fork main does not touch a PR. It only makes your notes stale on GitHub. In the main checkout, /sync-fork rebases it, pushes it, and lists which worktrees are behind upstream/main and by how many commits. Never press Sync fork on GitHub. It merges, and the daily rebase then fights it.

07

Rules that apply everywhere

  • Claude never commits. One exception: step 3 of /pr-update, on your yes to its report.
  • One push per round. Every push is one bot review run: 30 to 45 minutes, 3 to 8 dollars. A second push cancels the first run, so three quick pushes cost one run and give one review.
  • Never a plain --force. Always --force-with-lease.
  • Never cut a branch from fork main. The hook cuts from upstream/main. A branch made by hand uses git worktree add -b lukas/<slug> .worktrees/lukas/<slug> upstream/main.
  • Never the Sync fork button. /sync-fork instead.
  • Never a /fs- command on your own PR. The fix bot is refused on a fork PR, and the review bot already runs on every push.
  • Keep fullsend-no-fix on a bot PR from the moment you freeze it until the merge. At the latest, the approval puts it on.
  • Never commit or push on a pr/<N> branch. It is someone else's head. The next review round resets it hard, and a fix you tried there is gone on purpose.
  • Edit only where the guard line says. A worktree session edits its worktree. A --no-worktree session edits the main checkout. A plain claude in the main checkout reads and answers only.
  • Private files never enter a PR: lukas/, .claude/, .reviews/, .worktreeinclude, and the eight private skills. /pr-create checks. /sync-fork keeps the list in .git/info/exclude complete.
  • Nothing goes out red. SKIP=skillsaw uvx pre-commit run --all-files before every commit and every push. The one hook you skip is skillsaw: it fails locally on the private files, and in a worktree also on the linked skills. CI runs it on the real tree.
08

When it goes wrong

SymptomFix
gh says the token in keyring is invalid, or a skill fails on the first gh call gh auth login -h github.com. Every GitHub step in every skill needs it.
The guard line says MAIN checkout but you wanted a branch Exit. claude -w lukas/<n>-<slug>.
claude -w pr/N says cannot fetch upstream pull request N The number is wrong, or the network is down. Check with gh pr view N --repo redhat-et/protobot. The hook fetches from upstream, so git remote -v must list it.
Claude's git fetch or git push prints failed to store: 100001 or Operation not permitted The sandbox blocks the keychain helper and writes under .agents/skills. Let Claude re-run that one command with the sandbox off when it asks, or run it yourself: type ! git push --force-with-lease in the prompt.
git status in the main checkout shows D .agents/skills/<upstream skill>/SKILL.md An upstream skill file vanished from disk. Seen three times on 10 September 2026, cause unknown. Restore it before you commit: git checkout -- .agents/skills/<name>/SKILL.md. A private commit must never delete an upstream file.
/pr-create says a private file is in the diff Wrong base. Section 6, the wrong-base fix.
A /fs- command did nothing It must be the first word of a new top-level comment, from an account with write access. Then open the Actions tab, the newest fullsend run, the Route job: it prints the stage it picked or No stage matched.
--force-with-lease is refused Something moved the branch on the fork. git fetch origin, then git log HEAD..origin/lukas/<slug>. Look before you push again.
pre-commit is red Fix what it reports and run it again. Most hooks fix the file themselves; commit the result.
The bot approved, but the PR still says changes requested A human requested changes and a push never clears that. Ask that person for a re-review.
The fix bot stopped on a colleague's PR with needs-human Its automatic rounds are nearly used up. Take over: /pr-review N for a round, and hand-written /fs-fix <instructions> counts against the cap of 10.
git worktree remove refuses Another session holds the lock. Close it first. Do not delete the directory by hand.
A run finished but the bot posted nothing Its output failed the schema check, or the post step failed. The completion comment names the reason. Nothing to fix on your side.
