01

Three layers, and the line between them

A fork is not a copy. It is a place to keep two different kinds of work in one storage box. Your job is to make sure they never touch.

LayerLives onGoes to upstream?
Upstream code upstream/main It is upstream. You only read it.
A contribution branch lukas/<slug>, cut from upstream/main Yes, as one pull request.
Your private layer fork main, and your machine Never.

The picture below is the whole workflow. The top track is a contribution. The bottom track is your private layer. They share a storage box on GitHub and nothing else.

04

The daily loop

Six steps, in order. Steps 1 and 6 run in the main checkout. Steps 2 to 5 run inside one worktree.

  1. Catch up with upstream

    in ProtoBot/ — start it with claude --no-worktree

    Do this every morning, and again before you cut a new branch. Your notes commit is replayed on top of the newest upstream code.

    git fetch upstream --prune
git rebase upstream/main
git push --force-with-lease origin main

    The rebase never conflicts, because your commit touches only lukas/ and upstream never touches that path. The force push is safe: nobody else uses your fork's main.

  2. Start a feature in its own worktree

    from anywhere in the repo

    claude -w lukas/<slug>

    The hook makes .worktrees/lukas/<slug> on a new branch called lukas/<slug>. After the section 7 fix it cuts from upstream/main. To do it by hand instead:

    git fetch upstream
git worktree add -b lukas/<slug> .worktrees/lukas/<slug> upstream/main

    The worktree is that session's whole world. It never leaves the directory, and it never switches branch.

  3. Build and test it

    in .worktrees/lukas/<slug>

    A fresh worktree has no gitignored files, so install what the build needs there. AGENTS.md requires every pre-commit test to pass before you commit.

    pre-commit run --all-files

  4. Push the branch and open the pull request

    in the worktree

    git push -u origin lukas/<slug>
gh pr create --repo redhat-et/protobot \
  --base main --head lukaskellerstein:lukas/<slug>

    The branch lands in your fork. The pull request is opened against upstream. The repo's pull-request skill does the same thing with a checklist, so /pull-request is the shorter route.

    Before you push, prove the diff is clean:

    git diff --name-only upstream/main... | grep -E '^(lukas/|\.claude/)' # must print nothing

  5. Answer the review, then rebase

    in the worktree

    Upstream moves fast, so a pull request older than a day needs a rebase. Use /rebase-pr, or:

    git fetch upstream
git rebase upstream/main
git push --force-with-lease

  6. Clean up after the merge

    exit the session, then in ProtoBot/

    Pick remove when the session ends. That deletes the directory and keeps the branch. Then delete the branch yourself and refresh:

    git branch -D lukas/<slug>
git push origin --delete lukas/<slug>
git fetch upstream --prune
git rebase upstream/main
git push --force-with-lease origin main
Note on subagent worktrees

A subagent worktree at .worktrees/agent-<hex> is created but never removed automatically. Prune those by hand with git worktree list and git worktree remove.

05

Several agents at once

One worktree, one branch, one agent session. That is the unit. There is no limit beyond disk space, and git refuses to check out the same branch in two places, so the sessions cannot collide on a branch.

I checked what worktrees share in your repository. This matters, because it decides where you configure things.

Shared by every worktreePrivate to each worktree
.git/info/exclude — one edit covers all of them The working files themselves
.git/hooks/ — run pre-commit install once Gitignored files: build output, caches, .env
All commits, branches and remotes The checked-out branch and its index
A git fetch in one updates all of them Any running process, and its port

Two practical rules for parallel work:

  • Give each running app its own port. Two worktrees that start the same server fight over one port. Pick a free one and say which.
  • Re-read a file before you edit it. Two sessions can share one worktree. The other session's edits arrive as changed files on disk.

Your private files, and how each one travels

You have three kinds of private thing, and they need three different homes. Getting this wrong is what causes a leak.

WhatHomeHow it reaches a worktree
lukas/ notes Committed on fork main It does not. Read it at its path in the main checkout.
.claude/settings.json, .claude/hooks/, .claude/rules/ Not committed. The source of truth is mac-setup/projects/templates/claude/. Copied in by the WorktreeCreate hook, listed in .worktreeinclude.
Personal skills ~/.claude/skills/, already backed up in mac-setup They are global. Every session sees them.
Do not put a personal skill in this repo

.claude/skills is a symlink to .agents/skills, and that directory belongs to upstream. Anything you drop there is tracked and will show up in a pull request. Put personal skills in ~/.claude/skills/ instead.

Why the notes are committed but the tooling is not

The notes are about ProtoBot. They are worth backing up with the project, and nothing else on your machine produces them. The hooks and settings are machine-level templates that mac-setup delivers to every repository. Committing them here would create a second copy that drifts from the original.

07

Two gaps to close

Both are real today. Neither takes long.

Gap 1 — new worktrees branch from the wrong place

.claude/hooks/worktree-create.sh chooses its base from origin/HEAD. In a fork that is the dirty main. Fix it in the mac-setup template, then redeliver it here, so every forked repo on your machine gets the same behaviour.

# prefer the upstream remote when there is one
base=$(git -C "$root" symbolic-ref -q --short refs/remotes/upstream/HEAD 2>/dev/null || true)
[ -n "$base" ] || base=$(git -C "$root" symbolic-ref -q --short refs/remotes/origin/HEAD 2>/dev/null || true)

# fetch from whichever remote the base names
remote=${base%%/*}
branch=${base#*/}
git -C "$root" fetch -q "$remote" "$branch"

The repository already has refs/remotes/upstream/HEAD, so this works right away. In a repo with no upstream remote nothing changes.

Gap 2 — worktree sessions run with no Claude config

.worktrees/ears-manager/.claude/ holds only the skills symlink. There is no settings.json there, so inside a worktree session the worktree guard does not run, the sandbox setting does not apply, and the worktree hooks are not registered. The create hook already supports a fix; the file it looks for is simply missing.

Create .worktreeinclude in the repo root:

.claude/settings.json
.claude/hooks/*
.claude/rules/*

Then add the same paths to .git/info/exclude, so the copies never show up as untracked files in a feature branch:

/.claude/settings.json
/.claude/settings.local.json
/.claude/hooks/
/.claude/rules/
/.worktreeinclude
Why info/exclude and not .gitignore

.gitignore is tracked by upstream, so an entry there becomes a pull request. .git/info/exclude is local and, as I confirmed in your repo, shared by every worktree. One edit, every branch, nothing to send upstream.

What I rejected, and why

Two other designs are reasonable. I checked both against your repository and stayed with the plan above.

AlternativeWhat it givesWhy not
Push feature branches straight to upstream, since you have write access No cross-repo pull requests. Maintainers can push fixes to your branch. Nothing is lost by using the fork. I read the workflows: the CI job needs only contents: read, and the CodeRabbit job fires only for the fullsend-ai-coder bot. Your fork pull request #53 already merged. Keep upstream free of your branches.
Keep fork main an exact mirror, and put notes on a branch called lukas/base No force push. origin/main becomes safe to branch from. Once the hook cuts from upstream/main, the leak is gone anyway. Keeping the notes on main is what you asked for, and it costs one --force-with-lease a day.
Keep the notes as few commits

One commit that touches only lukas/ makes the daily rebase a no-op. If you add notes, amend that commit or add another one that also touches only lukas/. The moment a private commit touches an upstream file, your rebases start conflicting.

Command sheet

# --- catch up (main checkout, claude --no-worktree) ---
git fetch upstream --prune
git rebase upstream/main
git push --force-with-lease origin main

# --- start a feature ---
claude -w lukas/<slug>
# or by hand:
git worktree add -b lukas/<slug> .worktrees/lukas/<slug> upstream/main

# --- check the diff is clean, then ship (in the worktree) ---
git diff --name-only upstream/main... | grep -E '^(lukas/|\.claude/)'
pre-commit run --all-files
git push -u origin lukas/<slug>
gh pr create --repo redhat-et/protobot --base main \
  --head lukaskellerstein:lukas/<slug>

# --- refresh a live pull request ---
git fetch upstream && git rebase upstream/main && git push --force-with-lease

# --- after the merge (main checkout) ---
git branch -D lukas/<slug>
git push origin --delete lukas/<slug>

# --- see the state of everything ---
git worktree list
git branch -vv --all
git log --oneline upstream/main..main   # your private layer, should be tiny

When it goes wrong

SymptomFix
A pull request diff shows lukas/ The branch was cut from the wrong base. Rebase it onto the right one: git rebase --onto upstream/main main lukas/<slug>, then force-push.
git rebase upstream/main conflicts on main A private commit touched an upstream file. Find it with git log --stat upstream/main..main and split that change out into a real feature branch.
--force-with-lease is refused Something else moved origin/main. Run git fetch origin and look before you push again. Never fall back to a plain --force.
The worktree guard says you are in the main checkout You started without -w. Either restart with claude -w <name> for a branch, or with claude --no-worktree to work on main on purpose.
git worktree remove refuses Another session holds the lock. Close that session first. Do not delete the directory by hand.
Your fork's main looks far ahead of upstream on GitHub That is normal and expected. It is your notes commit plus commits upstream has since taken. Do not use the "Sync fork" button; it fights the rebase.
